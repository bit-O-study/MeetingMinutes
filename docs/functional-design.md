# 회의록 시스템 기능 설계안 v2

작성일: 2026-09-20 · 개정: 범위 재정의

> **v1에서 달라진 것**
> 사내 시스템 전제를 걷어냈다. 조직·팀·결재선·감사로그·보존정책·통계·확정 워크플로를 전부 제거하고,
> **여러 명이 같은 문서를 같이 쓰고 같이 관리하는 것**에 기능을 집중했다.
> 결제 기능은 설계 범위가 아니다.

---

## 1. 목적과 전제

- 소규모 그룹이 **같은 기록을 함께 작성하고 함께 관리**한다.
- 주 사용처는 다음 두 가지다.
  - **개발 스터디 회의** — 정기적으로 모여 학습 내용, 막힌 부분, 다음 회차 범위를 남긴다.
  - **인수인계 메모** — 업무를 넘기고 받을 때 절차·주의사항·미완료 건을 정리한다.
  - 그 밖의 가벼운 회의 메모, 개인 기록도 같은 구조로 담는다.
- 사용 인원은 그룹당 2~10명 수준을 가정한다. 조직 계층, 부서, 결재선은 두지 않는다.
- 승인받는 문서가 아니라 **같이 고쳐 나가는 문서**로 다룬다. 확정·재개정 개념을 두지 않는다.
- 웹을 기본으로 하고, 모바일에서는 조회와 할 일 체크를 지원한다.
- 이 문서는 기능 설계이며 구현 기술을 확정하지 않는다. 다만 실시간 공동 편집은 1차 필수 기능이므로 기술 선택에 제약이 된다.

### 하지 않는 것

| 제외 | 이유 |
| --- | --- |
| 결제·요금제 | 설계 범위 아님 |
| 조직·부서·팀 계층 | 그룹 하나가 곧 최소 단위 |
| 결재선·승인 워크플로 | 승인받는 문서가 아님 |
| 확정·재개정·버전 스냅샷 | 같이 고쳐 나가는 문서에는 방해가 됨. 변경 이력과 되돌리기로 대체 |
| 감사 로그·보존 정책 | 사내 규정 대상이 아님 |
| 운영 통계 대시보드 | 인원 규모에서 의미 없음 |

## 2. 기본 개념

세 가지만 있으면 된다.

```
스페이스 (개발 스터디 / 인수인계 / …)
  └─ 노트 (회차별 회의록, 인수인계 메모)
       └─ 할 일 (노트 안에서 만들고, 스페이스 단위로 모아 봄)
```

| 개념 | 설명 | 예 |
| --- | --- | --- |
| **스페이스** | 목적별 묶음. 멤버와 문서가 이 단위로 묶인다. | `프론트엔드 스터디`, `결제 모듈 인수인계` |
| **노트** | 스페이스 안의 문서 한 건. 회의록이든 메모든 같은 그릇. | `3회차 - useEffect 정리` |
| **할 일** | 노트 안에서 만든 체크 항목. 담당자·기한은 선택. | `다음 주까지 4장 읽기 @김OO` |

스페이스가 곧 권한 경계다. 스페이스에 속하면 그 안의 모든 노트를 읽고 쓸 수 있다.

## 3. 사용자와 권한

역할은 세 가지뿐이다.

| 역할 | 권한 |
| --- | --- |
| **스페이스 소유자** | 멤버 초대·제외, 스페이스 이름·삭제, 공유 링크 관리 |
| **멤버** | 스페이스 내 모든 노트 읽기·쓰기·할 일 관리, 노트 생성·삭제 |
| **링크 열람자** | 공유 링크로 들어온 사람. 해당 노트 1건만 읽기 전용 |

- 멤버끼리는 **권한 차등을 두지 않는다.** 스터디에서 누가 누구 글을 못 고치게 할 이유가 없고, 그걸 관리하는 비용이 더 크다.
- 노트 단위 접근 제어도 두지 않는다. 비공개가 필요하면 **스페이스를 따로 만든다.**
- 초대는 **초대 링크** 방식. 이메일 주소를 미리 알아야 하는 구조는 스터디에서 마찰이 크다.
- 소유자가 스페이스를 떠날 때는 다른 멤버에게 소유권을 넘긴다.

### 인수인계 메모의 주의

인수인계 메모에는 계정·접근 권한 이야기가 들어간다.
**비밀번호·토큰·키 값 자체를 적지 않는다**는 원칙을 템플릿과 화면 안내로 강제한다. "어디에 있는지, 누구에게 요청하는지"까지만 적는다.

## 4. 기본 사용 흐름

### 개발 스터디

1. 스터디장이 스페이스를 만들고 초대 링크를 공유한다.
2. 회차마다 스터디 회의록 템플릿으로 노트를 만든다.
3. **회의 중 여러 명이 동시에** 각자 배운 것과 질문을 적는다.
4. 막힌 질문은 해결 여부를 체크로 남긴다.
5. 다음 회차 범위와 발표자를 할 일로 만든다.
6. 다음 회차 노트를 열면 **지난 회차의 미완료 할 일과 미해결 질문이 연결되어 보인다.**

### 인수인계

1. 넘기는 사람이 스페이스를 만들고 받는 사람을 초대한다.
2. 인수인계 메모 템플릿으로 업무별 노트를 만든다.
3. 넘기는 사람이 초안을 쓰고, **받는 사람이 같은 문서에 질문을 바로 적는다.**
4. 답을 채워 가며 문서를 함께 완성한다.
5. 미완료 건은 할 일로 남겨 인계 후에도 추적한다.
6. 인계가 끝나면 노트를 `정리됨`으로 표시한다.

## 6. 템플릿

템플릿이 이 시스템의 실질적 가치다. 빈 문서를 주면 아무도 안 쓴다.

### 6.1 개발 스터디 회의록

```
■ 회차 / 날짜
■ 참석
■ 이번 범위          (책 챕터, 강의, 주제)
■ 발표·정리 담당

── 배운 것
   핵심 개념, 코드, 예시

── 막힌 것 · 질문       ☐ 해결 여부 체크
   질문 / 각자 답 / 결론

── 다음 회차
   범위 · 발표자 · 기한   → 할 일로 자동 전환
```

**설계 의도**
- `막힌 것`을 체크 항목으로 둔 이유: 스터디에서 실제로 가치 있는 기록은 "이해한 것"이 아니라 **"아직 이해 못 한 것"** 이다. 해결 여부를 추적하면 다음 회차의 논의거리가 자동으로 생긴다.
- `다음 회차` 항목은 입력하면 바로 할 일이 된다. 별도로 할 일을 또 만들게 하지 않는다.

### 6.2 인수인계 메모

```
■ 대상 업무
■ 인계자 / 인수자
■ 현재 상태          진행 중 / 완료 / 보류

── 이 업무가 하는 일
   한 문단 요약

── 접근 권한 · 계정
   ⚠ 값이 아니라 위치와 요청처만 적는다
   무엇이 필요한지 / 어디에 있는지 / 누구에게 요청하는지

── 정기적으로 하는 일
   주기 · 절차 · 확인 지점

── 주의사항 · 함정
   실수하기 쉬운 것, 과거에 터진 것

── 관련 문서 · 사람
   링크, 담당자

── 미완료 건           ☐ 할 일로 관리
```

**설계 의도**
- `주의사항 · 함정` 항목이 인수인계 문서의 핵심이다. 정상 절차는 문서나 코드를 보면 알 수 있지만, **"이건 이래서 이렇게 해야 한다"** 는 넘기는 사람 머릿속에만 있다.
- `접근 권한 · 계정` 블록은 입력란 위에 경고 문구를 고정 표시한다. 값을 붙여 넣으려는 순간 보이게 한다.

### 6.3 빈 노트

제목과 본문만. 형식 없는 기록용.

## 7. 상태와 규칙

### 7.1 노트 상태

`작성 중` → `정리됨`

- 두 단계뿐이다. 확정·승인 개념을 두지 않는다.
- `정리됨`으로 바꿔도 **계속 편집할 수 있다.** 목록에서 구분하기 위한 표시일 뿐이다.
- 누구나 바꿀 수 있다. 되돌릴 수도 있다.

### 7.2 할 일

`열림` → `완료`

- 담당자와 기한은 **선택 사항**이다. 스터디에서 "다음까지 4장 읽기"는 전원 대상이라 담당자가 없다.
- 담당자 없는 할 일은 스페이스 공용 할 일로 표시한다.
- 기한이 지나고 미완료면 지연으로 **표시**한다. 지연은 상태값이 아니라 계산 결과다.
- 완료한 항목은 되돌릴 수 있다.
- 노트를 삭제하면 그 노트의 할 일도 함께 삭제한다. 삭제 전 확인한다.

### 7.3 공동 편집

- 여러 명이 동시에 편집하며, 변경은 즉시 다른 사람 화면에 반영된다.
- **충돌 안내 화면이 없다.** 동시 편집이 전제이므로 편집 내용이 자동 병합된다. v1 설계의 저장 충돌 규칙은 이 방식에서 불필요해져 제거했다.
- 각자의 커서 위치와 선택 영역을 이름·색으로 표시한다.
- 연결이 끊기면 오프라인 상태를 표시하고, 입력은 로컬에 유지한다. 재연결 시 자동 반영한다.
- 저장 버튼을 두지 않는다. 대신 **연결 상태와 마지막 반영 시각**을 항상 보여 준다.

### 7.4 변경 이력

- 누가 언제 편집했는지를 시간순으로 남긴다.
- 특정 시점으로 되돌릴 수 있다. 되돌리기 자체도 이력에 남으므로 복구 가능하다.
- 확정 스냅샷 대신 이 이력이 v1의 버전 기능을 대체한다.

### 7.5 공유 링크

- 노트 단위, 읽기 전용.
- 만료 기한 설정, 언제든 회수.
- 링크 열람자에게는 할 일 체크·편집·이력을 노출하지 않는다.
- 링크가 살아 있는 동안 노트를 수정하면 수정본이 보인다. 공유 시점 고정이 아니다.

## 8. 핵심 화면

화면은 7개면 충분하다.

### 홈
- 내 스페이스 목록 (최근 활동 순)
- 최근 열어 본 노트
- 내 할 일 · 기한 임박
- 새 스페이스 / 새 노트

### 스페이스
- 노트 목록 (제목, 상태, 최근 수정자, 수정 시각)
- 멤버 목록 · 초대 링크
- 스페이스 할 일 모아 보기
- 새 노트 (템플릿 선택)

### 노트 편집 ← 핵심
- 상단: 제목, 상태, 현재 접속자, 연결 상태, 공유, 이력
- 본문: 템플릿 구조가 적용된 편집 영역
- 우측: 할 일 패널 (2차에 댓글, 3차에 전사 패널이 같은 자리에 들어감)
- 다른 사람의 커서와 이름이 실시간으로 보인다

### 내 할 일
- 스페이스 전체에서 나에게 배정된 항목
- 기한순 정렬, 지연 강조
- 체크 한 번으로 완료

### 검색
- 내가 속한 스페이스 전체 대상
- 제목·본문, 스페이스·기간 필터

### 변경 이력
- 시간순 목록, 시점 선택 조회, 되돌리기

### 공유 링크 관리
- 노트별 발급 링크, 만료, 회수

> **레이아웃 결정:** 노트 편집 화면은 처음부터 **본문 + 우측 보조 패널** 2분할로 만든다.
> 1차에는 할 일 패널, 2차에는 댓글, 3차에는 전사 타임라인이 같은 자리에 들어간다.
> 단일 컬럼으로 만들면 기능이 늘 때마다 핵심 화면을 다시 설계해야 한다.

## 10. 운영 기준

- 모든 요청에서 **스페이스 멤버십**을 검사한다. 확인할 것이 하나뿐이므로 누락 위험이 낮다.
- 공유 링크는 토큰으로만 접근하며, 회수 즉시 무효가 된다.
- 노트 삭제는 휴지통을 거친다. 30일 후 자동 삭제, 그 전에는 복원 가능.
- 스페이스 삭제는 소유자만 가능하며, 포함된 노트 전체가 휴지통으로 간다.
- 시간대는 `Asia/Seoul` 고정으로 표시한다.
- 인수인계 템플릿의 계정 블록에는 비밀번호·토큰 입력 금지 안내를 상시 노출한다.

## 11. 1차 완료 기준

- 이메일·비밀번호로 가입·로그인하고 스페이스를 만들 수 있다.
- 초대 링크로 다른 사람이 참여할 수 있다.
- **두 사람이 같은 노트를 동시에 열어 편집하면 서로의 입력이 실시간으로 보이고, 내용이 유실되지 않는다.**
- 저장 버튼 없이 입력이 보존되고, 새로고침 후에도 마지막 내용이 그대로다.
- 연결이 끊겼다 복구되면 오프라인 중 입력이 반영된다.
- 스터디 회의록 / 인수인계 메모 템플릿으로 노트를 만들 수 있다.
- 노트 안에서 만든 할 일이 담당자의 내 할 일에 나타난다.
- 변경 이력에서 이전 시점으로 되돌릴 수 있다.
- 스페이스에 속하지 않은 사람은 직접 URL로 노트를 볼 수 없다.
- 읽기 전용 공유 링크로 비로그인 사용자가 노트를 볼 수 있고, 회수하면 즉시 막힌다.

## 12. 구현 전 확정할 사항

v1의 11개 항목 중 8개가 범위 축소로 사라졌다. 남은 것은 세 가지다.

1. **실시간 공동 편집을 직접 구현할 것인가, 외부 서비스를 쓸 것인가.**
   직접 구현은 무료지만 서버 상태 관리가 필요하고, 외부 협업 서비스는 붙이기 쉬운 대신 무료 한도가 있다.
   *→ 인원 규모가 작으므로 직접 구현 권장.*

2. **로그인을 구글 계정만으로 할 것인가.**
   스터디원 중 구글 계정이 없는 사람이 없다면 이것만으로 충분하다. 추가하면 화면이 늘어난다.
   *→ 2026-09-21 사용자 결정: 이메일·비밀번호 자체 로그인으로 대체.*

3. **녹음·AI 정리를 언제 넣을 것인가.**
   기능 자체는 3차지만 노트 편집 화면 레이아웃에 영향을 준다.
   *→ §8의 2분할 레이아웃 결정으로 이미 대비함.*

## 13. 개인 일정·할 일 디자인 확장 (2026-10-26)

사용자 요청: 개인 일정과 직접 등록하는 할 일 메뉴를 설계하고, 할 일은 **기간 지정 또는 일정 픽스**가 가능해야 한다. 시안 검토 후 실제 앱 화면과 DB 저장까지 구현했다. 모아 Vercel 운영 배포는 별도 진행 상태이며 상세 검증 기록은 work-split.md에 기록한다.

### 메뉴와 시안

- PC: 기존 사이드바에 `개인 일정`을 추가하고 `내 할 일`을 확장한다.
- 모바일: `홈 · 일정 · 할 일 · 검색 · 나` 5개 하단 메뉴.
- 개인 일정: 월 달력 + 선택일 상세 목록. 작은 화면은 상세 목록을 달력 아래로 배치한다.
- 내 할 일: 개인 항목과 기존 프로젝트 담당 항목을 출처로 구분한다. 노트 할 일과 프로젝트 이슈 원본은 복제하지 않는다.
- 시안 파일: `docs/previews/personal-planner.html`. 외부 라이브러리·계정·네트워크 없이 열 수 있으며 화면 내 예시 데이터만 변경한다.
- 시안에서 홈·검색·계정은 기존 앱 연결 전임을 안내한다. 프로젝트 목록은 탐색 구조를 설명하는 표시용 예시다.
- 색상: 보라색 강조, 밝은 중립 배경, 둥근 카드. 기간은 녹색, 시간 확정은 보라색, 개인 약속은 주황색에 텍스트 분류를 함께 사용한다. 실제 앱 적용 시 기존 색상 토큰에 매핑한다.

### 일정 입력 규칙

| 방식 | 입력 | 의미 |
| --- | --- | --- |
| 기간 지정 | 시작일 선택, 마감일 필수 | 시작일부터 마감일까지 처리. 마감일만 지정 가능 |
| 일정 픽스 | 날짜, 시작·종료 시간 또는 종일 | 특정 시간에 수행할 일. 픽스는 편집 잠금이 아님 |
| 미정 | 날짜 없음 | 할 일 목록에만 표시하고 나중에 일정 지정 |

- 개인 일정은 날짜와 시간이 있는 약속으로 등록하며 종일을 지원한다. 할 일에는 세 방식을 모두 제공한다.
- 시간대는 Asia/Seoul. 기간 시작일과 마감일은 날짜로 저장하고, 시간 확정은 타임존이 있는 시각으로 저장한다.
- 기간형 마감일은 해당 서울 날짜 전체를 포함한다. 종일 확정 항목도 해당 서울 날짜 전체를 포함한다.
- 시작일이 마감일보다 늦거나 종료 시간이 시작 시간 이하이면 입력 위치에 오류를 표시한다. 1차 시간 확정 입력은 같은 날짜 내에서만 지원한다.
- 방식 변경 시 이전 방식의 필드를 서버에서도 비우고 활성 방식에 맞는 값만 저장한다.
- 목록·달력·선택일 상세는 동일 레코드를 읽는다. 완료 체크는 할 일에만 제공한다.
- 지연은 저장 상태가 아니라 미완료와 마감 경과 여부로 계산한다. 필터는 미완료/완료/전체이고 지연은 그룹 제목 또는 표시로만 표현한다.
- 기간형: 서울 날짜가 마감일 다음 날이 되면 지연. 시간 확정형: 종료 시각 경과 후 지연. 종일: 다음 서울 날짜부터 지연. 미정은 지연 판정하지 않는다.

### 실제 구현을 위한 데이터·권한 설계

개인 항목은 프로젝트 참여와 무관하게 본인만 조회·수정한다. 기존 §3의 스페이스 권한은 프로젝트 문서에 유지하고, 개인 일정 영역에만 사용자 소유권 경계를 추가한다.

- 신규 `personal_planner_items` 제안: id, ownerId, kind(event/task), title, memo, scheduleMode(none/range/fixed), startDate, endDate, scheduledDate, startsAt, endsAt, allDay, doneAt, createdAt, updatedAt, version.
- kind=event는 fixed만, kind=task는 세 방식 모두 허용한다. 날짜/시간 필드의 상호 배타성과 순서 검증은 서버 및 DB 제약으로 보장한다.
- ownerId는 로그인 세션에서만 결정한다. 조회·변경·삭제·건수 집계 모두 ownerId 조건을 포함한다. ID를 알아도 타 사용자 항목은 존재 여부를 노출하지 않는다.
- 달력 조회는 시작일이 화면 밖인 기간도 겹치면 포함한다. 날짜가 없는 할 일은 달력에서 제외한다.
- 기존 tasks와 issues는 원본 그대로 유지하며 개인 할 일만 신규 테이블에 둔다. 통합 목록 키는 원본 종류와 id를 조합하고 각각의 기존 권한 검사/액션을 사용한다.
- 목록은 페이지 단위 조회, 기간 달력은 보이는 월 범위 조회. 요약 수치는 페이지 결과 길이가 아니라 소유권 조건이 있는 전체 집계로 계산한다.
- 생성은 요청 ID로 중복 제출을 방지한다. 수정은 version 비교로 다른 기기에서의 변경 덮어쓰기를 방지하고 재조회 안내를 제공한다.
- 실제 화면에서는 유효한 입력을 자동 반영하고 저장 중/저장됨/실패를 표시한다. 디자인 시안의 `미리보기에 추가`는 체험용 동작으로 실제 저장 버튼을 뜻하지 않는다. 초기 입력은 제목과 해당 방식의 필수값을 만족한 뒤 한 번 생성한다.
- 1차 제외: 반복 일정, 외부 캘린더 동기화, 푸시 알림, 드래그 이동, 개인 항목 공유. 시안의 추가·완료 동작은 메모리 내에서만 처리한다.

### 검수와 적용 순서

1. 시안: 월 이동, 날짜 선택, 일정/할 일 탭, 기간·시간 입력, 완료 필터, 오류 안내, 모바일 배치 검토.
2. 데이터: 소유권·스키마·액션·기존 데이터와의 분리 및 서버 검증 구현.
3. 화면: `/calendar`와 `/tasks`에 적용, 사이드바·모바일 메뉴·홈·배지 연결.
4. 통합 검증: 두 사용자 사이의 조회/수정 차단, 자정 경계, 월을 가로지르는 기간, 중복 제출, 저장 실패 재시도, 기존 프로젝트 할 일·이슈 회귀 확인.

시안 검증 스크립트: `node docs/previews/verify-planner.cjs`. 1440px 데스크톱과 390px/320px 모바일, 마감일 단독 등록, 기간·시간 역전 오류, 완료 필터, Escape 닫기, 가로 넘침과 페이지 오류를 확인한다. 실제 앱 DB·인증 연동 검증을 대신하지 않는다.
